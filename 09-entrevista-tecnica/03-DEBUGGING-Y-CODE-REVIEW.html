Debugging y code review: encuentra el error

En muchas entrevistas te muestran código y te preguntan: "¿qué está mal aquí?" o "¿qué le dirías a quien lo escribió?". Evalúan si conoces las trampas del lenguaje y si revisas con criterio: corrección, seguridad, rendimiento y legibilidad.

Cómo practicar: lee cada fragmento, escribe qué falla, con qué entrada falla y cómo lo corriges. Después abre la respuesta. Si puedes, ejecuta el fragmento para comprobarlo.

Cómo responder en la entrevista: (1) qué hace mal, (2) un ejemplo de entrada que lo rompe, (3) la corrección, (4) cómo evitarías que vuelva a pasar, por ejemplo con una prueba o una regla del linter.

Python

1. La lista que recuerda

def agregar_nota(nota, notas=[]):
    notas.append(nota)
    return notas

print(agregar_nota(8))
print(agregar_nota(9))   # el autor esperaba [9]
Respuesta

Imprime [8] y luego [8, 9]. El valor por defecto se crea una sola vez, al definir la función, y todas las llamadas comparten la misma lista mutable. Corrección: def agregar_nota(nota, notas=None): y dentro if notas is None: notas = []. Pylint lo detecta (W0102, dangerous-default-value).

2. Borrar mientras recorres

def quitar_reprobados(notas):
    for n in notas:
        if n < 7:
            notas.remove(n)
    return notas

print(quitar_reprobados([5, 6, 8, 9]))
Respuesta

Devuelve [6, 8, 9]: el 6 se salva. Al borrar el 5, todos los elementos se corren una posición y el bucle salta el siguiente. Además modifica la lista que recibió, un efecto secundario sorpresa. Corrección: crear una lista nueva, return [n for n in notas if n >= 7]. Regla: nunca modifiques una colección mientras la recorres.

3. La búsqueda que no encuentra el último

def buscar(lista, x):
    izq, der = 0, len(lista) - 1
    while izq < der:
        medio = (izq + der) // 2
        if lista[medio] == x:
            return medio
        if lista[medio] < x:
            izq = medio + 1
        else:
            der = medio - 1
    return -1

print(buscar([1, 3, 5], 5))
Respuesta

Devuelve -1. Cuando izq == der todavía queda un elemento por revisar, pero el bucle termina antes. Es un error off-by-one. Corrección: while izq <= der. Prueba siempre con el primer elemento, el último, uno que no existe y una lista vacía.

4. El promedio que explota

def promedio(notas):
    return sum(notas) / len(notas)

promedio([])
Respuesta

ZeroDivisionError con una lista vacía. Hay que decidir y documentar qué pasa en ese caso: devolver None o 0, o lanzar un ValueError con un mensaje claro. Por ejemplo: if not notas: return None. Es el caso de borde que más se olvida.

5. Dinero con float

subtotal = 0.1 + 0.2
if subtotal == 0.3:
    print("cobrar 0.30")
print(1.10 * 3)
Respuesta

No imprime "cobrar" y la multiplicación da 3.3000000000000003. Un float es binario y no representa exactamente 0.1. Para dinero usa Decimal("0.10") (construido desde texto) o enteros en centavos; para comparar floats, math.isclose(a, b). En SQL: DECIMAL(10, 2), nunca FLOAT.

6. is en vez de ==

codigo = input("Código: ")       # el usuario escribe LAB-001
if codigo is "LAB-001":
    print("encontrado")
Respuesta

Casi nunca imprime "encontrado". is compara identidad (si son el mismo objeto en memoria), no igualdad de valor, y el texto leído es un objeto distinto. Python 3.8+ incluso muestra un SyntaxWarning. Usa == para valores; is solo para None, True y False.

7. La matriz con filas clonadas

tablero = [[0] * 3] * 3
tablero[0][0] = 1
print(tablero)
Respuesta

Imprime [[1, 0, 0], [1, 0, 0], [1, 0, 0]]: * 3 repite la misma lista tres veces, así que las tres filas son una sola. Corrección: [[0] * 3 for _ in range(3)]. Es la misma idea que copia superficial vs profunda (copy.deepcopy).

8. Horarios comparados como texto

def se_cruzan(ini1, fin1, ini2, fin2):
    return ini1 < fin2 and ini2 < fin1

print(se_cruzan("9:00", "10:00", "9:30", "11:00"))   # se cruzan, ¿verdad?
Respuesta

Devuelve False. Los textos se comparan carácter por carácter, y "9:00" < "11:00" es falso porque "9" > "1". Comparar horas como texto solo funciona si siempre tienen dos dígitos (09:00). Corrección: validar el formato con ^([01]\d|2[0-3]):[0-5]\d$ (como en 08-guia-desde-cero) o convertir a minutos: h * 60 + m.

9. Consulta armada con f-string

def buscar_docente(db, nombre):
    sql = f"SELECT * FROM docentes WHERE nombre = '{nombre}'"
    return db.execute(sql).fetchall()

buscar_docente(db, "x' OR '1'='1")
Respuesta

Inyección SQL: con esa entrada la consulta queda WHERE nombre = 'x' OR '1'='1' y devuelve todos los registros. Con otras entradas un atacante puede leer otras tablas o borrar datos. Corrección: consulta parametrizada, db.execute("SELECT * FROM docentes WHERE nombre = ?", (nombre,)). Nunca concatenes entrada del usuario en SQL. Es el número 1 que revisan en un code review.

10. El reporte que hace 1 001 consultas

labs = db.execute("SELECT id, nombre FROM laboratorios").fetchall()
reporte = []
for lab in labs:
    total = db.execute("SELECT COUNT(*) FROM reservas WHERE laboratorio_id = ?",
                       (lab["id"],)).fetchone()[0]
    reporte.append((lab["nombre"], total))
Respuesta

Funciona, pero es el problema N+1: una consulta para la lista y una más por cada laboratorio. Con 1 000 laboratorios son 1 001 viajes a la base de datos. Corrección, una sola consulta: SELECT l.nombre, COUNT(r.id) FROM laboratorios l LEFT JOIN reservas r ON r.laboratorio_id = l.id GROUP BY l.id. El LEFT JOIN conserva los laboratorios con 0 reservas. Los ORMs esconden este problema; se soluciona con joinedload o include.

JavaScript

11. Igualdad con conversión

function validarCantidad(cantidad) {
  if (cantidad == "") return "La cantidad es obligatoria";
  return "OK";
}
console.log(validarCantidad(0));
Respuesta

Devuelve "La cantidad es obligatoria". Con ==, JS convierte los tipos: 0 == "" es true (también "0" == false y null == undefined). Usa siempre ===. Para validar: if (cantidad === "" || cantidad === null || Number.isNaN(Number(cantidad))). ESLint lo exige con la regla eqeqeq.

12. sort que ordena mal

const edades = [10, 9, 1, 100];
console.log(edades.sort());
Respuesta

Imprime [1, 10, 100, 9]: sin comparador, sort convierte todo a texto y ordena alfabéticamente. Corrección: edades.sort((a, b) => a - b). Ojo: sort también modifica el arreglo original; si no quieres eso, usa [...edades].sort(...) o toSorted.

13. forEach con async

async function guardarTodas(reservas) {
  reservas.forEach(async (r) => {
    await db.guardar(r);
  });
  console.log("Todas guardadas");
}
Respuesta

"Todas guardadas" se imprime antes de guardar, y los errores de guardar se pierden: forEach no espera promesas. Corrección en serie: for (const r of reservas) await db.guardar(r);. En paralelo: await Promise.all(reservas.map((r) => db.guardar(r)));.

14. El await que falta

async function saludar(email) {
  const usuario = buscarUsuario(email);   // buscarUsuario es async
  if (!usuario) return "No existe";
  return `Hola ${usuario.nombre}`;
}
Respuesta

Siempre devuelve "Hola undefined". Sin await, usuario es una Promise, que siempre es truthy, y una promesa no tiene .nombre. Corrección: const usuario = await buscarUsuario(email);. TypeScript o la regla de ESLint no-floating-promises lo detectan.

15. var en un bucle

for (var i = 1; i <= 3; i++) {
  setTimeout(() => console.log("Turno", i), 100);
}
Respuesta

Imprime "Turno 4" tres veces. var tiene alcance de función, así que las tres funciones comparten la misma i, y cuando se ejecutan el bucle ya terminó con i = 4. Corrección: let i, que crea una variable nueva en cada vuelta. En Python pasa lo mismo con [lambda: i for i in range(3)]; se corrige con lambda i=i: i.

Ejercicio de code review

Te piden revisar este pull request. Antes de ver la respuesta, encuentra al menos 8 problemas y ordénalos por gravedad.

import sqlite3
from flask import Flask, request

app = Flask(__name__)
app.secret_key = "123"

@app.route("/reservas", methods=["GET", "POST"])
def reservas():
    db = sqlite3.connect("app.db")
    if request.method == "POST":
        docente = request.form["docente"]
        lab = request.form["lab"]
        fecha = request.form["fecha"]
        ini = request.form["ini"]
        fin = request.form["fin"]
        db.execute(f"INSERT INTO reservas VALUES (null, {lab}, '{docente}', '{fecha}', '{ini}', '{fin}')")
        db.commit()
    filas = db.execute("SELECT * FROM reservas").fetchall()
    html = ""
    for f in filas:
        lab = db.execute(f"SELECT nombre FROM laboratorios WHERE id = {f[1]}").fetchone()
        html += f"<li>{f[2]} - {lab[0]} - {f[3]} {f[4]}-{f[5]}</li>"
    return "<ul>" + html + "</ul>"
Respuesta (12 problemas, del más grave al menos grave)
  1. Inyección SQL en el INSERT y en el SELECT del bucle (f-strings). Usar parámetros ?.
  2. XSS: docente se inserta en el HTML sin escapar; un nombre como <script>…</script> se ejecuta en el navegador de cada visitante. Usar plantillas Jinja, que escapan por defecto, o markupsafe.escape.
  3. Clave secreta débil y escrita en el código ("123"). Leerla de una variable de entorno: os.environ["SECRET_KEY"].
  4. Sin validación: campos vacíos, formato de fecha y hora, fin > ini, que el laboratorio exista y no esté en mantenimiento.
  5. No revisa choques de horario: es la regla de negocio principal (ini1 < fin2 AND ini2 < fin1).
  6. Sin CSRF en un formulario POST (Flask-WTF o un token propio).
  7. request.form["x"] lanza KeyError → error 400 genérico si falta un campo; mejor request.form.get("x", "").strip() con un mensaje de error claro.
  8. La conexión nunca se cierra: se pierde en cada petición. Usar g + teardown_appcontext o with.
  9. N+1: una consulta por cada reserva para traer el nombre del laboratorio. Usar JOIN.
  10. Después del POST no hay redirect (patrón Post/Redirect/Get): al recargar la página se duplica la reserva.
  11. INSERT sin nombres de columnas, SELECT * e índices mágicos (f[1], f[2]) se rompen si cambia la tabla. Nombrar las columnas y usar row_factory = sqlite3.Row.
  12. Sin pruebas, sin paginación y sin separación de responsabilidades: la ruta valida, guarda y genera HTML. Separar en validaciones.py, db.py y plantillas, como en 08-guia-desde-cero.

Cómo comunicarlo: empieza por lo bueno ("la ruta es corta y se entiende"), separa lo que bloquea el merge (1–5) de las sugerencias (10–12) y propone la corrección en lugar de solo señalar el problema.

Checklist para revisar código (úsala también con tu propio código)

Área Pregunta
Corrección ¿Hace lo que dice el requisito? ¿Funciona con vacíos, nulos, bordes y errores de red o de base de datos?
Seguridad ¿Consultas parametrizadas? ¿Salida escapada? ¿Secretos fuera del código? ¿Se valida en el servidor? ¿Se revisa quién puede hacer qué?
Rendimiento ¿Consultas dentro de bucles (N+1)? ¿Bucles anidados innecesarios? ¿Falta paginación o índices?
Legibilidad ¿Nombres claros? ¿Funciones cortas con una sola tarea? ¿Código duplicado? ¿Números mágicos?
Errores ¿Se manejan las excepciones? ¿Los mensajes ayudan al usuario sin exponer detalles internos?
Pruebas ¿Hay pruebas de las reglas de negocio? ¿Cubren los casos de borde?
